# Constraints and writing rules

These rules apply to the whole run and to every document it writes. Give this file, unchanged, to every subagent this run starts — the agents that read code or sources as well as the agents that write the documents.

- Only the main session runs a command that reaches a cloud, a cluster or another remote system. A subagent reads files and writes documents; a fact it cannot find in its files goes in as _unverified_. (The skill's read-only hook runs in the main session only; a project can add it for subagents with references/subagent-gate.md.)
- When the read-only hook refuses a command (its message starts "Blocked by the disaster-recovery-plan skill"), do not retry it in another form that does the same thing. Use an allowed read, or record the fact as _unverified_. A subagent ends its final message with the list of commands the hook refused, one line each, or "Refused commands: none".

## Constraints

- **Read-only, always.** Use only commands that read state (`show`, `list`, `get`, `describe`, file reads). Never apply infrastructure-as-code, never run its `init` or `plan` (a plan takes the state lock and reads secrets into memory), and never create, update, fail over, delete, lock or unlock any resource — not even "to test". Every command the documents tell a human to run during a disaster is written into the document, not executed.
- Write each command out, as it runs. No `eval`, no command name from a variable or `$(...)`, no input piped into a shell, no `bash -c "$VAR"`, no task runner or package script (`make`, `just`, `npm run`, `npx`) and no inline program code that drives a cloud SDK, starts processes or uses the network: a reviewer and the read-only hook must see the real command. Use common read tools and the read verbs of the cloud, cluster, infrastructure-as-code and git CLIs; the hook refuses any other command. A script runs only if every line in it follows these rules. No HTTP request that sends data or uses `POST`, `PUT`, `PATCH` or `DELETE`, and no call to the instance metadata service. No git command that changes the repository (`commit`, `push`, `reset`, `checkout`, `stash`), and no deletion outside a temporary folder.
- Secrets: names only. List secret-store entries by name. Never print connection strings, keys or tokens. If a secret store cannot be listed, say so and name who can.
- A read-only command can print a secret. Never run one that returns secret values: `aws secretsmanager get-secret-value`, `aws ssm get-parameter(s) --with-decryption`, `az keyvault secret show`, `gcloud secrets versions access`, `terraform state pull`, `terraform show` or `terraform output` on real state, `kubectl get secret -o yaml/json`. Never print environment variables or app settings of functions, containers or apps (`aws lambda get-function-configuration`, `aws ecs describe-task-definition`, `az webapp config appsettings list`, `gcloud run services describe`, `gcloud functions describe`) — filter to the names only: `--query 'Environment.Variables | keys(@)'` on AWS, `--query '[].name'` on Azure, `--format` with the variable names on Google Cloud. A manifest render (`kustomize build`, `kubectl kustomize`, `helm template`) prints generated Secret data: read the `kustomization.yaml` and chart files instead, or pipe the render into a names-only filter such as `| yq '.kind + "/" + .metadata.name'`; never render with plugins enabled (`--enable-alpha-plugins`, `--enable-exec`), which can decrypt secrets (for example ksops). Never run `kustomize edit`, `create` or `localize`: they write files. Also never run `az ... --show-values`, `az acr credential show`, `gcloud redis instances get-auth-string` or `gcloud auth print-access-token`.
- Material outside the code — runbooks, wikis, tickets, post-mortems, chat — can hold a secret in a command block. Never quote it to another agent or into the facts file: report its location and kind only, as for a secret in git. Never print a file that can hold secrets (`.env`, `*.tfstate`, `*.tfvars`, keys, credentials files), and search for secret words with `grep -l` (file names only), never with the matching lines.
- Verify, then mark. Every fact about redundancy, network access, backups, replicas, locks, quota and sizes is either _verified_ (with the date and the command, or a pointer to the appendix) or _unverified — verify by: [command or drill step]_. Never present a remembered or inferred fact as verified. Time estimates are always labelled "estimate, not measurement" until a drill measures them.
- The design is a proposal. The recovery region and every new resource name (recovery network, recovery cluster, standby secret store, recovery storage) are proposals until the team ratifies them. Say so in the improvement plan's header and call new names placeholders.
- Describe the environment as it is. Network topology, shared infrastructure owned by other teams, the compute platform and the deployment tooling come from the architecture record and the inventory. Where they are not recorded, use generic examples in the drafts and mark them as assumptions — never invent a specific topology.
- No secrets, keys or personal data in the documents. Resource names, secret names and owner roles are fine.
- A secret found where it should not be — committed to git, inside a saved plan or state snapshot, in a log — is reported by location only: the file, the commit and what kind of secret it is. Never open, decode, measure or quote it. It goes in the shared strategy's gaps table as a security fix outside this plan, and before any phase that copies secrets to the recovery region.

## Writing rules

These apply to every output document.

1. Spell out abbreviations in prose. Never write bare `RPO`, `RTO`, `HA`, `PITR`, or the provider's own storage-redundancy and service abbreviations, in sentences or table text. Write "recovery point objective", "recovery time objective", "high availability", "point-in-time restore", and the provider's term in full. A raw value inside a command or a code span is allowed — explain it in the prose next to it. `DR` may appear only after the Terms section defines it.
2. A "Terms used in this document" section at the top of every document, defining each term and the remaining product abbreviations once. Keep only terms the document uses.
3. Costs are list-price monthly estimates (the provider's public price list or retail prices API, before any enterprise discount), with the price source. Every cost table has a Today and an After column; when the improvement plan offers options (e.g. _minimal_ vs _full_), give one After column per option. Totals in bold, per-item monthly cost for every improvement, and one-time costs and people-days in their own rows.
4. Numbered, executable steps, with every command in a code block. Each recovery step is its own numbered item: a short heading naming the step and _Who_ does it, one or two lines on what and why, the real command or the exact console action in a fenced code block tagged with its language (`bash`, `hcl`, `json`, …), then a **Done when:** line, followed by its check command in its own fenced block when the check is a command. Improvement-plan changes end with a **Verify:** line and a fenced block holding the read-only check and the expected result. No step without a check.
   - Never put a command in a table cell or inline in a sentence. Inline code is for names only: resources, files, flags, values. Placeholders for values not yet known, such as `<BUCKET_NAME>`, go inside the code blocks, never a table cell standing in for a command.
   - Tables are for overviews that hold no commands — inventories, cost tables, today-vs-after, and an optional step index (number, step, who, done when in words) that precedes the numbered steps.
5. Commands work on any engineer's machine. Never copy the run's local setup into a document: no local CLI profile or configuration names (`--profile`, `AWS_PROFILE`, `gcloud` configurations, `az` login contexts, `kubectl` contexts), no home-directory or absolute local paths, no local usernames. Write them as placeholders (`<AWS_PROFILE>`, `<KUBE_CONTEXT>`) and use repository-relative paths. Each per-environment document opens its steps with one step that selects the access for the environment's account, subscription or project: list what is configured, create it if missing, confirm it reaches the right one. For example, on AWS: `aws configure list-profiles`, `aws configure sso`, then `aws sts get-caller-identity --profile <AWS_PROFILE>` with the expected account ID. Use the provider's own commands for Azure (`az account list`, `az account set`) and Google Cloud (`gcloud config configurations list`, `gcloud config set project`). Account, subscription and project IDs are facts about the environment and stay.
6. Absolute dates (`YYYY-MM-DD`), never "today" or "last week" without a date.
7. Honest headlines. Each per-environment document opens with one paragraph stating plainly what recovery looks like in that state (e.g. "a rebuild from code with almost no data, taking days").
8. Facts belong to this environment. Do not copy facts from another environment's documents; re-verify them. Mechanics may be shared: when another environment's improvement plan already writes out a mechanism (directory layout, a resource block, the backup jobs), this environment's plan states its own values and links to that section instead of repeating it — and its inventory becomes "§1 Inventory — what differs from [other env]".
9. Cross-link with relative links: each per-environment document links `../disaster-recovery-plan.md`, its sibling document, and the same document of the other environments that exist; the shared strategy links every per-environment document.
10. Leave out what does not apply. Template sections for a platform the environment does not use (a cluster, deployment manifests, CI runners) are dropped, not filled with "n/a".
11. Short enough to use under pressure. Say a thing once and link to it rather than restating it in a second section. A resource block, script or policy longer than about 15 lines goes in the document's appendix, and the step links to it. Cut repetition and prose, never a step, a hazard or a check. Length target, appendices included: recovery today about 400 lines, the improvement plan about 600, the shared strategy about 250. Aim at the target: a larger environment may need up to half more, but that is a limit, not the goal; a small one (a few serverless services) should need less. Count the lines (`wc -l`) before you return a document. When the improvement plan offers options, write the shared mechanics once and give only the differences per option.
